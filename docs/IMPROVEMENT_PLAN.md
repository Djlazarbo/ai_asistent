# План улучшений Job Hunter (после аудита 22.11.2026)

Порядок — по влиянию на жалобу «вакансии не очень мониторятся». Правила неизменны: одна БД (изоляция через user_*), никаких глобальных фильтров/порога/опыта hh, не ломать non-PM роли, секреты не коммитить.

## Фаза 0 — диагностика (0,5–1 день)

1. **Кнопка «Почему мало вакансий?»** в профиле: per-user разбор — резюме? keywords (сколько реально уходит в поиск после фильтров)? каналы? monitoring? порог?; сколько новых за 7 дней; топ-причин скипов.
2. **Владельцу в jh_digest**: per-user «новых за сутки», флаг «лента не растёт N дней».

## Фаза 1 — «лента дышит без нажатий» (1–2 дня, главный эффект)

3. **Периодический per-user backfill** каждые 2–3 ч: `backfill_user_feed(days=1..2, limit=20)` для search-ready юзеров — чужие находки и крон-инжест сами подтекают в ленту.
4. **Инкрементальный HH каждые 60–90 мин** (1–2 конфига, окно от последнего прогона с перекрытием; вечерний марафон остаётся).
5. **Опция «Мгновенные пуши»** (`ears_freq=instant`) — `tg_notify` работает с 1.2.1; дефолт не меняем.

## Фаза 2 — качество подбора (≈ неделя)

6. Онбординг: «Взять слова из резюме» (`merge_keywords_from_profile`) с превью/правкой.
7. Рекомендованные TG-каналы (курируемый владельцем список) — одна кнопка «Добавить».
8. Обучение блок-листа: после 3+ скипов компании предлагать «Не показывать {company}».
9. Getmatch: починить парсер или честно понизить приоритет.
10. Per-user опыт hh / порог — кнопкой в профиле, только по запросу юзера (docs/TASKS.md).

## Фаза 3 — развитие (P2)

Еженедельная сводка per-user · повторный отклик через N дней · аналитика удержания (last_seen) · честный ETA очереди · алерт jh_monitor «48ч не растёт лента у search-ready» · лимиты docker-логов (max-size).

# Поиск по вакансиям: почему «криво» и что чинить (добавлено 22.11.2026)

Жалоба: «поиск работает криво или не настроен». Проверил на проде — частично подтверждается, это не ощущение.

## Найденные факты (прод, 22.11.2026)

### Факт 1: keywords молча отбрасываются фильтром
У Ilsiyar82 из 10 keywords два — «Управление it проектами» и «Управление ит проектами» — **тихо выкидываются** на каждом поиске: `title_filter.is_search_keyword()` режет фразы, начинающиеся с «управление …» (долговые фразы), и юзер об этом не узнаёт. Настройки показывают 10 слов — работает 8. Это прямой ответ на «или не настроен».

### Факт 2: сверхширокие keywords заливают выдачу мусором
«Руководитель отдела», «Руководитель проекта», «Менеджер проектов» (Ilsiyar82) матчат любые отрасли → сотни нерелевантных карточек на скрейпе, которые потом режут junk/off-PM фильтры и DeepSeek (трата запросов и времени), а часть просачивается в ленту со скором 1–3. Наблюдается как «поиск кривой»: то пусто, то мусор.

### Факт 3: глобальный junk-фильтр режет чужие роли на инжесте
`_JUNK_TITLE` в `title_filter.py` содержит `backend|frontend|fullstack|разработчик` и др. — вырезается на уровне ОБЩЕГО пула. Сейчас все трое — PM-поискатели, им ок. Но стоит юзеру искать «frontend разработчик» — он не увидит ничего в принципе (правило «не ломать non-PM роли» уже нарушено архитектурой фильтра).

### Факт 4: daily-поиск ищет по union всех юзеров
Ночной cron (`_scheduled_run`) без chat-контекста: keywords = объединение всех, строится ОДНА boolean-команда `NAME:(…) NOT продажам NOT маркетинг …` (PM-режим), `days_back` = min(дней с прошлого прогона +1, 3) — обычно 1 день; окно без перекрытия → простой/сдвиг крона = потерянные вакансии. Персональный `salary_from` в union-контексте читается из legacy-глобальной настройки — теоретически чужой фильтр применился бы ко всем (сейчас никем не задан).

### Факт 5: PM boolean ищет только по NAME:
`NAME:(kw1 OR kw2 …)` — вакансии, где роль в тексте, а не в заголовке, не находятся. Для ручных PM-запросов это заметно сужает выдачу.

### Факт 6: Getmatch фактически полумёртв
`no __NEXT_DATA__` (сайт сменил разметку) — 5 вакансий/сутки проскакивает. В отчёте юзеру выглядит как «источник есть, толку нет».

## План фиксов поиска (P1, по порядку)

**S1. Валидация keywords при сохранении (обязательное, ~0,5 дня).**
При добавлении/сохранении keywords прогонять каждое через `is_search_keyword` и `vacancy_matches_user`-эвристику: показывать юзеру «⚠️ эти слова не будут искать: … (долговая фраза)» и «⚠️ слишком широкое: "Руководитель отдела" — будет много мусора, уточните: Руководитель IT отдела». Плюс одноразовая кнопка «Проверить мои слова» для существующих юзеров. Закрывает Факты 1–2.

**S2. Диагностика поиска per-user (~0,5 дня).**
Расширение пункта 1 фазы 0: показать юзеру его эффективный запрос к HH (что реально уйдёт после фильтров), применённые исключения и статистику воронки последнего поиска (найдено → junk → дубликат → fan-out miss → в ленту). Владельцу — то же по любому юзеру.

**S3. Junk-фильтр per-user на fan-out, не на инжесте (~1 день).**
Dev/маркетинг/безопасность-роли не вырезать из пула: инжест пишет всё, junk/off-PM фильтры применяются в `vacancy_matches_user` по профилю юзера (PM-поискатель — режет; non-PM — нет). Закрывает Факт 3, снимает риск для будущих non-PM юзеров. Требует аккуратности с объёмом пула (TTL уже есть).

**S4. Честный daily-поиск (~0,5 дня).**
Окно с перекрытием (`last_poll − 12h`), salary-фильтр в union-прогоне игнорировать (только в личных «Искать сейчас»), `NOT`-исключения оставить только для PM-запроса. Закрывает Факт 4.

**S5. Дублирующий запрос по text= для PM (~0,5 дня, опционально).**
После NAME:-прогона один дополнительный запрос `text=(…) NOT …` с меньшим числом страниц — ловит вакансии с ролью в описании. Следить за антиботом hh (частота).

**S6. Getmatch: починить или понижать (~0,5–1 день).**
Посмотреть актуальную разметку; если SPA без данных — перевести на их публичный JSON/API, иначе убрать из текста «Искать сейчас» упоминание источника, чтобы не обещать.

**Приоритет внедрения: S1 → S2 → S4 → S3 → S6 → S5.** S1+S2 сразу дают юзерам понимание «что ищется на самом деле», S4+S3 чинят потерянные/вырезанные вакансии.

## Чего в поиске НЕ делаем

- Не включать чужой salary/порог/опыт друг другу (только per-user, по запросу).
- Не заменять Playwright-скрейп на api.hh.ru (OAuth с 2025-12-15 недоступен) и не крутить частоту до бан-риска: инкрементальные прогоны — с паузами и 1 страницей на конфиг.
- Не чистить keywords юзеров молча: только уведомления и подсказки.
